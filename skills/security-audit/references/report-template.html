6. Before you apply a fix

  • Every code change in this report is a suggestion. Nobody applied it, and nobody ran the tests of the project on it.
  • Some fixes change how the app works for its users. Each finding says so under “What the fix changes for users”.
  • Write the test first. It must fail before the fix and pass after it.
  • Apply one fix at a time, and run the whole test suite after each one.

The scale

LabelMeaning
CriticalWide and direct harm with little or no access needed: control of accounts, of the system, or of the main data of many users.
HighSerious harm to real users or data, and the attacker needs only what a normal user can get.
MediumReal harm, but limited: it stays inside one account or one group, or it needs a strong condition first.
LowA real defect with a small effect, or one that needs unusual conditions.
InfoNo direct harm. A weak habit or a missing safety net that is worth knowing.
ConfidenceHow sure the models are that the finding is real. High: the whole path was read in the code. Medium: one part was not read or depends on a condition. Low: likely, but the story has a gap.
Verify firstA fact outside the code decides the real risk. The finding says which fact, and what to do for each answer.
Two viewsThe models do not fully agree. Both views are printed inside the finding.
